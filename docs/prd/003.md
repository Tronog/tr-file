# Overview (FIXES)

# Section 1
- Bugs in the existing code:
  - A symlink to a folder opens as a file preview instead of navigating into it (file-browser.feature.ts:172).
  - Memory leak: cached images are never freed. The function that frees them is never called, so every previewed image (up to 32 MiB each) stays in memory for the whole session.
  - On the desktop, reading, uploading and downloading all load the whole file into memory, sometimes twice.
  - Download errors only go to the browser console, and downloads never appear in the Transfers panel.
  - Listing a folder checks each entry one after another, which will be slow for big folders. Nothing in the UI renders only the visible rows either.
  - Files are shown as text unless their extension is on a list of binary types, so .docx, .sqlite and similar files render as garbage.
  - Sorting puts file10 before file2.

# Section 2
- Security, which matters before adding delete and move:
  - The server deployment has no login at all.
    - implement simple username password, but for desktop should be optional (disabled by default on desktop)
  - The upload endpoint can be triggered by any website a user visits (cross-site request forgery).
  - The desktop app still serves the full, unprotected API on a local port, even though its own window no longer uses it. Any local program, or a web page that finds the port, could read and write files.

# Section 3
- Components built but never connected: the right-click menu component is never used, the menu bar has no handler for clicks, the activity bar's Search and Bookmarks buttons do nothing, and the Places pane is empty.

# Section 4
- Decisions to make before building the missing operations:
  - Whether to keep one confined root folder or support several roots and absolute paths.
  - One shared way to run long jobs and push progress to the UI, which file watching can reuse.
  - A single command table that the menus, right-click menus, command palette and shortcuts all read from.
